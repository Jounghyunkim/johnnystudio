# ADR-0008: 가입은 이메일 인증, 그다음부터는 이메일 + 비밀번호로 로그인한다

- **상태**: 채택됨
- **날짜**: 2026-11-06
- **대체**: [ADR-0007](0007-magic-link-auth-api.md) 결정 1의 "비밀번호는 없다" (메일 링크 구조·FastAPI·세션·CSRF·CSP 결정은 그대로다)
- **관련**: [ARCHITECTURE.md](../ARCHITECTURE.md) §4, [개인정보처리방침](../../../content/pages/privacy.md)

## 맥락

- ADR-0007 은 매직 링크만으로 가입·로그인하게 했다. 사용자가 다음처럼 지적했다 (2026-11-06).
  "가입은 이메일 인증으로 하더라도, 그 뒤 로그인까지 매번 메일 인증을 거치는 것은 비효율적이다. 가입한 이메일로, 또는 아이디·비밀번호로 로그인하게 해 달라."
- 세션은 30일 동안 유지되므로, 같은 브라우저에서는 매번 메일이 필요하지는 않았다. 다만 새 기기나 브라우저에서 로그인하거나, 30일이 지나거나, 로그아웃한 뒤에는 메일을 기다려야 했다.
- 운영 DB 는 아직 없다 (서버 설치 전). 개발 SQLite 만 있다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 매직 링크만 유지 (ADR-0007) | 지킬 비밀이 없다 | 사용자가 비효율적이라고 판단했다. 메일이 늦거나 스팸함에 가면 로그인이 막힌다 |
| **이메일 인증으로 가입 → 비밀번호 설정, 로그인은 이메일 + 비밀번호** | 가입 때 주소가 진짜인지 확인한다. 그 뒤 로그인은 메일이 필요 없다. 비밀번호 관리 프로그램과 잘 맞는다 | 비밀번호 해시를 지켜야 한다. 대입 공격 대비가 필요하다 |
| 아이디(별도 사용자 이름) + 비밀번호 | 이메일을 드러내지 않는 이름 | 받는 정보가 늘어난다 (R8). 아이디 찾기 흐름이 하나 더 필요하다. 1인 포털에서 얻는 것이 적다 |
| 가입 폼에서 이메일 + 비밀번호를 함께 받고 인증 메일로 활성화 (Arkurator 방식) | 익숙하다 | 인증하지 않은 계정과 그 비밀번호 해시를 쌓아 둔다 |

## 결정

1. **아이디는 이메일이다.** 별도 사용자 이름은 받지 않는다.
2. **가입**: `/signup/` 에서 이메일 → 인증 메일(`purpose=signup`) → `/login/verify/` 에서 '계속하기' → 같은 화면에서 비밀번호를 정한다.
   - 계정은 링크를 눌렀을 때 만든다 (ADR-0007 과 같다). 인증되지 않은 계정과 비밀번호는 저장하지 않는다.
   - 비밀번호를 정하지 않고 창을 닫아도 계정은 있다. 그때는 재설정 링크로 비밀번호를 정한다.
3. **로그인**: `/login/` 에서 이메일 + 비밀번호 (`POST /api/auth/login`).
   - 틀린 비밀번호, 없는 이메일, 비밀번호가 없는 계정 모두 같은 응답을 준다. 없는 계정에도 해시 계산만큼 시간을 써서, 응답 시간으로도 가입 여부를 알 수 없게 한다.
4. **비밀번호를 잊었을 때**: `/login/reset/` 에서 링크(`purpose=reset`)를 받아 새 비밀번호를 정한다. 비밀번호를 바꾸지 않고 그 링크로 로그인만 할 수도 있다 (메일 링크 로그인은 남는다).
5. **비밀번호 변경** (`POST /api/account/password`)
   - 비밀번호가 이미 있으면 현재 비밀번호가 맞아야 바꿀 수 있다.
   - 예외: 메일 링크로 방금 로그인한 세션(링크 유효 시간 15분 안, 한 번만)은 현재 비밀번호 없이 정할 수 있다. 이것이 가입·재설정 경로다.
   - 바꾸면 그 기기를 뺀 모든 세션을 끊는다.
6. **해시**: 표준 라이브러리 `hashlib.scrypt`, N=2^17·r=8·p=1 (OWASP 권장값, 메모리 128MiB, M8 에서 약 0.5초).
   - 형식은 `scrypt$17$8$1$소금$해시` 이다. 강도를 올리면 다음 로그인 때 다시 해시한다.
   - 새 의존성이 없다. argon2-cffi 는 하위 패키지 3개를 들여와서 쓰지 않았다.
7. **규칙** (NIST SP 800-63B 방향)
   - 10~128자이고, 조합 규칙은 두지 않는다. 입력은 NFKC 로 정규화한다.
   - 너무 흔한 것, 이메일(아이디 부분)과 비슷한 것은 거부한다. 붙여 넣기와 비밀번호 관리 프로그램을 막지 않는다 (`autocomplete` 를 정확히 준다).
8. **대입 공격**
   - 실패를 `login_failures` 에 남긴다. 같은 이메일로 15분에 5번, 같은 IP 에서 1시간에 20번 틀리면 잠시 막는다.
   - 메일 링크 로그인은 막지 않는다. 남이 일부러 틀려서 잠가도 주인은 들어올 수 있다. 기록은 하루 뒤 지운다.
9. **스키마**: 운영 DB 가 아직 없어서 테이블을 그대로 고쳤다.
   - 개발 SQLite 는 스키마가 코드와 다르면 스스로 지우고 다시 만든다 (시험용 계정이 지워진다).
   - 운영 DB 는 절대 지우지 않고 시작을 멈춘다. **운영에 처음 설치한 뒤의 변경부터 Alembic 을 쓴다** (ADR-0007 의 "처음 바꿀 때 Alembic" 을 이렇게 고친다).

## 결과

- **좋아지는 점**: 가입 뒤에는 메일 없이 바로 로그인한다. 메일 발송이 멈춰도 기존 회원은 로그인할 수 있다.
- **감수할 점**
  - 비밀번호 해시가 DB 에 생겼다. DB 백업도 그만큼 조심해서 다뤄야 한다. 개인정보처리방침을 고쳤다.
  - 로그인 한 번에 CPU 0.5초, 메모리 128MiB 를 쓴다. 요청 제한이 동시 요청을 줄인다.
  - 같은 이메일로 일부러 비밀번호를 틀려서 비밀번호 로그인을 잠글 수 있다. 메일 링크 로그인으로 피해 간다.
- 2단계 인증(TOTP 등)은 아직 없다. Client Room(Phase 3)에서 의뢰인 자료를 다루기 전에 다시 본다.

## 재검토 조건

- Client Room 도입 (2단계 인증, 관리자 계정 보호)
- 운영 DB 에 처음 설치한 뒤 스키마를 바꿀 때 → Alembic
- 로그인 요청이 많아 scrypt 비용이 부담될 때
