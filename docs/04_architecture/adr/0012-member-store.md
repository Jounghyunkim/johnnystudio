# ADR-0012: 회원 Store: 회원이 올린 Windows 앱을 운영자 승인 후 공개한다

- **상태**: 제안됨
- **날짜**: 2026-11-24
- **관련**: [ADR-0011](0011-absorb-johnnystore.md) (결정 2·6, 결정 4 의 신고·관리자·이용약관을 대체), [JohnnyStore 통합 검토](../../02_planning/features/johnnystore-integration.md) §2-3·§6 S5,
  [Store 기능 명세](../../02_planning/features/store.md), [ideation §8](../../ideation.md) (하지 않을 것), [ADR-0004](0004-nextjs-static-export.md) (정적 내보내기),
  [ADR-0005](0005-file-based-content.md) (파일 콘텐츠), [ADR-0007](0007-magic-link-auth-api.md) · [ADR-0008](0008-password-login.md) (회원 API)

## 맥락

- 사용자 요청 (2026-11-24): "기존에 검토했던 JohnnyStore를 JohnnyStudio의 하나의 메뉴로 추가하고 싶다. 그래서 사용자들도 스토어에 zip 또는 exe 파일등을 업로드하고 접속하는 사용자들이 사용해볼 수 있는 그런 공간을 추가해줘. 기존 johnnystore의 기능 및 개념을 녹여서 구현해 줘."
- 2026-11-22 의 ADR-0011 은 "파일을 올리는 사람은 운영자뿐"(결정 2), "운영 서버에 웹으로 파일을 올리는 길은 만들지 않는다"(결정 6), "신고·관리자·이용약관은 가져오지 않는다"(결정 4)로 정했다.
  재검토 조건은 "다른 사람의 파일을 받아야 할 일이 생길 때: 새 ADR 로 비목표를 바꾸고, 별도 다운로드 도메인·이용약관·신고 절차를 먼저 정한다 (검토 문서 S5)"였다.
- ideation §8 의 하지 않을 것: "의뢰인이 아닌 사람의 파일 업로드는 받지 않는다."
- 웹은 정적 내보내기다 (ADR-0004). 회원이 올리고 운영자가 승인하는 앱은 빌드 없이 바뀌므로 빌드된 HTML 에 넣을 수 없다.
  AGENTS.md 의 "콘텐츠는 빌드된 HTML 에 들어 있어야 한다"는 운영자 콘텐츠(`content/`, ADR-0005)를 전제로 한 규칙이다.
- 서버가 필요한 일은 회원 API(FastAPI, `api/`)만 맡는다 (ADR-0007). 로그인은 이메일 인증 + 비밀번호, httpOnly 세션 쿠키, Origin 검사가 이미 있다.
- JohnnyStore 보관본(`johnnystore 6dc01fe`)에 설치 파일 분석기(`pe_extractor.py`, 테스트 포함), 이용약관 문안, 분류·신고 사유, 공개 범위·다운로드 토큰 코드가 있다.
- 사이트는 Cloudflare 를 거친다 (ADR-0006). 요청 본문 한도가 있다 (무료 요금제 100MB `[확인 필요]`, 통합 검토 문서 X6).
- 1인 운영이다 (ideation R1). 2026-11-24 확인: 서버(M8)에 ClamAV 가 설치되어 있지 않다, 디스크 여유 75GB.
- 같은 날 사용자 답 (네 가지 질문):
  - Q1 공개 방식 → **운영자 승인 후 공개** (권장안)
  - Q2 '사용해 보기' 범위 → **Windows 프로그램 내려받기** (권장안. 브라우저에서 실행하는 웹 zip 은 하지 않음)
  - Q3 회원 파일의 주소 → **지금은 johnnystudio.net** (권장안. 나중에 별도 도메인으로 옮길 수 있게)
  - Q4 메뉴 이름 → **Store** (권장안. 주소 `/store/`)

## 검토한 선택지

공개 방식 (Q1)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **운영자 승인 후 공개** | 악성·불법 파일이 공개되기 전에 막는다. 1인 운영에서 위험이 가장 낮다 | 검토가 상시 업무가 된다. 공개가 늦어진다 |
| 올리면 바로 공개 + 신고 (JohnnyStore 방식) | 올리는 사람이 편하다. 운영자 손이 덜 간다 | 신고가 오기 전까지 남의 파일이 포털 도메인에서 나간다 |
| 허락한 회원만 올림 (퍼블리셔 승인제) | 믿는 사람만 올린다 | 처음 오는 개발자는 올릴 수 없다. 허락한 뒤의 파일은 검토하지 않는다 |

'사용해 보기' 범위 (Q2)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **Windows 프로그램 내려받기** (.exe .msi .msix .zip .7z) | JohnnyStore 와 같다. 사이트 안에서 남의 코드를 실행하지 않는다 | 브라우저에서 바로 써 볼 수 없다 |
| + 웹 zip 을 브라우저에서 실행 | 설치 없이 써 본다 | 남의 HTML/JS 를 실행하므로 별도 등록 도메인의 샌드박스가 꼭 있어야 한다. 일이 크게 늘어난다 |

회원 파일을 내줄 주소 (Q3)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **지금은 같은 도메인, 내려받기 전용으로. 설정으로 옮길 수 있게** | 도메인·Tunnel 을 더 준비하지 않아도 된다 | 악성 파일이 하나라도 공개되면 포털 도메인 전체가 브라우저 위험 경고(Safe Browsing 등)를 받을 수 있다 |
| 별도 등록 도메인부터 | 평판이 분리된다 (검토 문서 S5 의 원래 계획) | 도메인 구입·Tunnel 설정을 사용자가 먼저 해야 한다 |

회원 앱 화면을 그리는 방식

| 선택지 | 장점 | 단점 |
|---|---|---|
| **정적 셸 + 브라우저에서 API 로 읽기** | ADR-0004 그대로. 승인하면 바로 보인다 | 빌드된 HTML 에 앱 정보가 없다 (검색엔진 노출을 기대하기 어렵다, JS 필요) |
| 승인할 때마다 다시 빌드·배포 | 앱마다 정적 페이지 | 승인이 배포가 된다. 회원 글이 git·빌드에 들어간다 |
| Next 서버 모드 | 서버에서 그린다 | ADR-0004·0007 을 뒤집는다. 해시 CSP·정적 배포를 다시 짠다 |

## 결정

1. **하지 않을 것을 바꾼다.** 회원이 Windows 프로그램 파일(.exe .msi .msix .zip .7z)을 올리고, 방문자가 내려받는다. 브라우저에서 실행하는 업로드(웹 zip)는 받지 않는다.
2. **새 앱과 새 버전은 운영자가 승인해야 공개된다** (Q1). 검토 중인 앱은 올린 사람과 운영자에게만 보이고, 남에게는 404 다.
   공개된 앱의 이름·소개·설명·아이콘 수정은 바로 반영하고, 신고·숨김으로 사후 대응한다.
3. **올리는 사람**: 이메일 인증한 회원. 처음 올리기 전에 표시 이름(공개)을 정하고, Store 이용약관 동의와 만 14세 이상 확인을 한다. 이메일은 공개하지 않는다.
   **운영자**는 설정 `JOHNNYSTUDIO_STORE_ADMINS` 의 이메일이다. 역할 테이블은 만들지 않는다.
4. **바이러스 검사**: 서버 안의 ClamAV(`clamscan`)로, 올린 뒤 응답과 따로 돈다. 상주 `clamd`·VirusTotal API 는 쓰지 않는다 (통합 검토 문서 Q6 의 판단 그대로).
   운영은 검사 결과가 '탐지 없음'이어야 승인할 수 있다 (`JOHNNYSTUDIO_STORE_REQUIRE_SCAN`, 운영 기본값 켬). 탐지되면 공개된 버전이어도 바로 반려하고 파일을 지운다.
   화면에는 엔진·시그니처·검사일을 쓰고 '안전'을 보장한다고 쓰지 않는다. VirusTotal 은 방문자가 직접 여는 검색 링크만 둔다.
5. **설치 파일 분석**: JohnnyStore 의 `pe_extractor.py` 를 `api/app/store/analyze.py` 로 옮긴다 (이름·버전·아키텍처·서명 블록·아이콘).
   의존성 4개(pefile 2024.8.26, icoextract 0.3.1, pillow 13.0.0, olefile 0.47)를 정확한 버전으로 고정한다.
   남의 파일을 파싱하므로 API 프로세스가 아니라 **자식 프로세스에서 시간·메모리 한도를 걸고** 돌린다. 확장자와 실제 내용이 다르면 받지 않는다.
   아이콘(파일에서 뽑은 것, 회원이 직접 올린 것)은 Pillow 로 256px PNG 로 다시 그린 것만 내준다.
6. **올리기**: 8MB 조각으로 받는다 (Cloudflare 요청 한도 아래). 한도는 설정으로 둔다: 파일 하나 300MB, 회원 한 명이 올려 둔 합계 2GB, 24시간에 10번
   `[확인 필요: 구현하면서 정한 기본값, 사용자 확인 전]`. 문제가 생기면 `JOHNNYSTUDIO_STORE_UPLOADS_OPEN=0` 으로 새 업로드만 막는다.
7. **내려받기**: API 가 공개 여부를 확인한 뒤 nginx 에 넘긴다 (`X-Accel-Redirect`, internal location `/_store_files/`). 저장 이름은 무작위 키이고,
   응답은 항상 `attachment` · `application/octet-stream` · `nosniff` · `CSP: sandbox` 다.
   **지금은 johnnystudio.net 에서 낸다** (Q3). `JOHNNYSTUDIO_STORE_FILES_ORIGIN` 을 정하면 공개 내려받기 링크만 다른 등록 도메인을 가리킨다 (그 도메인의 nginx 는 내려받기 경로만 연다).
   검토용 내려받기는 로그인 쿠키가 필요해서 사이트 주소에 남는다.
8. **화면**: 주 메뉴 **Store** (`/store/`, Q4). Library 다음에 둔다. 페이지는 정적 셸이고, 목록·상세·내 앱·검토는 브라우저에서 `/api/store/` 로 읽는다.
   **AGENTS.md "콘텐츠는 빌드된 HTML 에" 규칙의 예외**로 기록한다 (회원 콘텐츠만). 운영자 작품은 지금처럼 Library 와 `content/` 에 둔다 (ADR-0005 유지).
   회원이 쓴 글은 글자로만 그린다 (HTML 로 넣지 않는다).
9. **신고·숨김·차단**: 누구나(로그인 없이도) 신고한다 (같은 IP 1시간 5번). 운영자는 앱을 숨기고, 회원을 차단한다 (차단하면 그 회원의 앱이 모두 목록에서 빠지고 새로 올릴 수 없다).
   권리 침해 신고는 「저작권법」 제103조 절차를 따른다 (Store 이용약관 제9조, JohnnyStore 약관 문안을 옮김).
10. **데이터**: 기존 `users` 테이블은 바꾸지 않고 `store_*` 테이블 5개(올리는 회원·앱·버전·업로드·신고)를 더한다. 파일은 `/opt/johnnystudio/store/` (개발은 `api/data/store/`).
    회원이 탈퇴하면 그 회원의 앱·파일을 바로 지운다. 신고 기록은 연결만 끊고, 처리한 뒤 1년 지나면 지운다 `[확인 필요: 보관 기간]`.
11. 그대로 두는 것: "JohnnyStore" 이름은 쓰지 않는다 (ADR-0011 결정 9). 비공개 공유(링크 전용·접근 코드)는 Phase 3 Client Room 으로 (결정 5). 운영자 작품은 관리 도구로만 올린다 (결정 3).

## 결과

- **좋아지는 점**
  - JohnnyStore 의 "누구나 올리고 링크로 받는" 목표를 JohnnyStudio 의 인증·디자인·CSP·배포 위에서 다시 연다. 스토어의 낮은 보안 수준(localStorage JWT, 이메일 인증 없음, CSP 없음)은 가져오지 않는다
  - 공개 전에 사람이 한 번 본다. 검사·분석·검토 결과가 화면에 남아 Trust by Design 을 지킨다
  - 회원 콘텐츠와 운영자 콘텐츠가 섞이지 않는다 (Store ↔ Library)
- **감수할 점**
  - 검토·신고 처리가 운영자의 상시 업무가 된다 (ideation R1)
  - 같은 도메인이라, 승인한 파일에 악성이 섞이면 포털 도메인 평판이 떨어질 수 있다. 하위 도메인만으로 평판이 분리되는지는 확인하지 않았다 `[확인 필요]`
  - 남의 파일을 배포하는 법적 책임: 저작권법상 온라인서비스제공자 책임 제한 요건, 약관 법률 검토를 하지 않았다 `[확인 필요]`
  - Store 앱 정보는 빌드된 HTML 에 없어서 검색엔진 노출을 기대하기 어렵다 (목록 페이지의 안내 문구만 있다)
  - 홈 회선 대역폭·디스크를 회원 파일이 쓴다 (ideation R7). `clamscan` 은 실행할 때마다 시그니처를 메모리에 올린다 `[확인 필요: 메모리·시간]`
  - 공개된 앱의 글 수정은 사후 대응이다
  - 운영 서버에 ClamAV 설치와 운영자 이메일 설정 전에는 (운영 기본값에서) 아무 앱도 승인할 수 없다 → deploy/README §3-7

## 재검토 조건

- 승인한 파일에서 악성코드가 나오거나, 포털 도메인이 브라우저 위험 경고를 받으면: 바로 업로드를 닫고(`STORE_UPLOADS_OPEN=0`), `STORE_FILES_ORIGIN` 으로 별도 등록 도메인으로 옮긴다
- 검토·신고가 운영자가 감당할 양을 넘으면: 허락한 회원만 올리기(퍼블리셔 승인제)나 초대제로 좁힌다
- 회원 앱을 검색엔진에 노출해야 하면: 앱마다 정적 페이지 생성 또는 서버 모드를 검토한다 (ADR-0004 의 재검토)
- 브라우저에서 실행하는 앱(웹 zip)을 받으려면: 별도 등록 도메인의 샌드박스를 먼저 정한다 (새 ADR)
- 대역폭·디스크가 모자라면: 외부 저장소·CDN 을 검토한다 (Cloudflare 약관의 대용량 바이너리 조건 `[확인 필요]`)
- 약관 법률 검토 결과가 나오면: 약관·신고 절차·보관 기간을 고친다
