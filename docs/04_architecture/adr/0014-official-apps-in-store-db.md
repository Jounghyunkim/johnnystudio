# ADR-0014: 운영자의 공식 앱·서비스도 Store·Showroom DB 에서 관리한다

- **상태**: 제안됨
- **날짜**: 2026-11-26
- **관련**: [ADR-0012](0012-member-store.md) 결정 8·12 (Store DB 에 사본을 만들지 않는다 → 이 ADR 이 부분 대체), [ADR-0005](0005-file-based-content.md) (작품은 파일),
  [ADR-0009](0009-local-portfolio-manager.md) (작품 관리 도구), [Store](../../02_planning/features/store.md) · [Showroom](../../02_planning/features/showroom.md) 명세

## 맥락

- 사용자 요청 (2026-11-26): "현재 관리자인 내가 올렸던 앱들에 대해서도 DB로 관리될 수 있도록 마이그레이션 해주세요."
- 지금 Store·Showroom 의 '공식' 항목(Windows 앱 11개, 웹 서비스 Arkurator)은 Library 작품 파일(`content/assets`)을 빌드할 때 함께 보여 준 것이다 (ADR-0012 결정 8).
  그래서 고치기·새 버전·지우기를 웹 화면에서 할 수 없고, 개발 서버의 작품 관리 도구(토큰)와 다시 빌드·배포가 필요하다. 출시 빌드에는 관리 도구가 없다.
- ADR-0012 는 "원본이 둘이 되면 버전·체크섬이 어긋나고, 운영 DB 에서는 다시 비어 있다"는 이유로 DB 사본을 만들지 않았다.
- 같은 날 정한 것 (사용자 선택)
  - Library 의 소개 글·그림은 작품 파일에 그대로 두고, **설치 파일·버전은 Store DB 한 곳**에서 관리한다. Library 의 내려받기는 Store 앱 화면으로 잇는다
  - 옮길 것: Store 앱 11개 + Showroom 의 Arkurator
  - 운영자 계정이 올린 앱·서비스에는 계속 **'공식'** 표시를 단다
  - Store 에 이미 있던 운영자 앱 'My Claude Inspector' 0.1.2 의 파일이 소개 자료 zip 이었다 → 진짜 설치 파일로 바꾼다

## 결정

1. **공식 = 운영자 계정이 올린 것.** API 가 앱·서비스 응답에 `official` 을 낸다 (주인의 이메일이 `JOHNNYSTUDIO_STORE_ADMINS` 에 있으면 true). 화면은 '공식' 표시를 달고,
   상세의 "회원이 올린 앱입니다" 안내 대신 "JohnnyStudio가 직접 만든 앱입니다"를 보인다. 공식 서비스의 링크는 회원 링크(`ugc`)로 다루지 않는다. DB 에 열을 더하지 않는다.
2. **원본**: 설치 파일·버전·검사 결과·소개 자료(Store 에 보이는 것)는 DB 가 원본이다. Library 의 소개 글·그림·태그는 작품 파일이 원본이다.
   옮긴 작품 파일에는 `storeApp: <코드>`(데스크톱 툴), `showroomService: <코드>`(웹 서비스)를 적는다.
   - Library 상세: `storeApp` 이 있으면 작품 파일의 `downloads` 대신 **'Store에서 내려받기'**(→ `/store/app/?id=<코드>`)를 보인다. `showroomService` 가 있으면 'Showroom 소개'로 잇는다
   - Store·Showroom 목록은 코드가 있는 작품을 작품 파일에서 다시 합치지 않는다 (DB 의 것만, 중복 없음). 코드가 없는 데스크톱 툴은 지금처럼 작품 파일에서 '공식'으로 합친다
   - 작품 파일의 `downloads` 는 남긴다: Library 에는 보이지 않고, **DB 를 새로 채울 때의 처음 버전**으로만 쓴다 (개발 DB 는 스키마가 바뀌면 다시 만들어지고, 운영 DB 는 아직 없다)
3. **옮기는 길**: `scripts/import-official.sh` (여러 번 돌려도 된다).
   1. web 작품 관리 CLI `official-export` 가 작품 파일을 스키마로 검사해 JSON 으로 낸다 (API 에 YAML 해석기를 들이지 않는다)
   2. `api/app/import_official.py` 가 회원 업로드와 같은 길로 DB 를 채운다: 크기·SHA-256 을 작품 파일과 맞춰 보고, 확장자·내용 검사, 자식 프로세스 분석, Store 보관 폴더로 **복사**(원본은 그대로),
      ClamAV 검사(탐지되면 공개 안 함, 검사가 필요한 설정에서 '탐지 없음'이 아니면 검토 대기), 아이콘·그림 다시 그리기, 소개 자료 정리(한도).
      본문의 그림만 있는 줄은 소개 그림 모음으로 옮긴다 (Store 설명은 그림을 글자로만 보인다)
   3. CLI `official-link` 가 코드를 작품 파일에 적는다 (머리말의 다른 줄은 그대로)
   - 이미 있으면 건너뛴다: 작품 파일의 코드, 없으면 같은 운영자의 같은 이름(서비스는 주소). 작품 파일에 코드가 있는데 DB 에 없으면 **같은 코드로 다시 만든다** (Library 링크가 그대로 맞는다)
   - `--fix-files`: 이미 있는 앱의 같은 버전 파일이 작품 파일과 다르면 작품 파일의 것으로 바꾼다 (코드·소개 자료는 그대로, 옛 파일은 지운다)
4. **그 뒤의 관리**는 회원 앱과 같다: 새 버전은 Store 의 '새 버전 올리기', 고치기·지우기는 Store·Showroom 화면과 검토 화면 (운영자). 작품 관리 도구의 `downloads` 는 고쳐도 Library 에 보이지 않는다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 소개 글은 Library, 설치 파일·버전은 Store DB (채택)** | 웹 화면에서 새 버전·고치기·지우기. 파일은 한 곳. Library 상세는 그대로 | 작품 파일의 `downloads` 가 처음 버전으로 남는다 (DB 를 새로 채울 때만 쓴다) |
| B. Library 에서도 빼고 DB 만 | 원본이 하나 | Library 에서 데스크톱 툴이 사라진다 (빌드된 HTML 에 없게 된다) |
| C. 두 곳 모두 그대로 (DB 사본) | 바꿀 것이 적다 | 버전을 바꿀 때 두 곳을 함께 고쳐야 한다 (ADR-0012 가 피하려던 방식) |
| 공식 판단: 운영자 계정 (채택) / DB 에 열 추가 | 열을 더하지 않는다 (개발 DB 가 지워지지 않는다) | 운영자 이메일 설정을 바꾸면 표시가 따라 바뀐다 |

## 결과

- **좋아지는 점**: 운영자 앱도 출시 사이트에서 바로 새 버전·고치기·지우기를 한다. 내려받기 수·검사 결과·SHA-256 이 회원 앱과 같은 화면에 있다.
- **나빠지는 점·주의**
  - 운영 DB 를 만든 뒤 `scripts/import-official.sh` 를 한 번 돌려야 한다 (deploy/README.md §3-8). 그때는 작품 파일의 처음 버전이 들어가므로,
    개발 DB 에서 올린 새 버전은 운영에서 다시 올린다 (DB 끼리 옮기는 도구는 없다)
  - Store 에서 공식 앱을 지우면 Library 의 'Store에서 내려받기'가 없는 주소를 가리킨다. Library 에서도 빼려면 작품 파일의 `storeApp` 줄을 지운다 (그러면 작품 파일의 다운로드가 다시 보인다)
  - 설치 파일이 두 곳에 있다: 다운로드 보관 폴더(`/files/`, 작품 파일의 원본)와 Store 보관 폴더(`store/files`). 개발에서 321MB
- **재검토 조건**: 작품 파일의 `downloads` 와 DB 버전이 자주 어긋나 헷갈리면, 옮긴 작품의 `downloads` 를 지우고 DB 백업으로 운영 DB 를 채우는 길을 검토한다
